* Handoff — CRS work in Geosetta

Orientation doc for an agent picking up the coordinate-reference-system (CRS)
work. Read this, then =plans/crs-registry.org= (the design plan) — it and the
rest of this crate's design docs live in =plans/=.

** READ THIS FIRST — WHAT HAS CHANGED SINCE
Everything below is an accurate record of how the registry was *built*, and
its § KEY FINDINGS is still the best account of what was tried and rejected.
Two things it describes are no longer the present tense:

1. *The =crs-registry= Cargo feature is gone.* =geosetta= 0.24.0 removed the
   feature and its dependency on this crate outright. The two compose over a
   *pipe* now (=geosetta --print-crs-code= / =geosetta --crs <path|->=), not a
   linked optional dependency — see
   =geosetta/plans/crs-external-resolution.org=. Anywhere below that says
   "behind a =crs-registry= feature" or "the feature-off build", read it as
   history.
2. *Name recovery lives here now, not in =geosetta=.* R2's
   =resolve_geographic_by_name= / =resolve_projected_by_name= (described below
   as =geosetta/src/crs/registry.rs=) were deleted with that crate's registry
   module and reimplemented here as =identify_from_wkt=
   ([[file:plans/wkt-identify.org][plans/wkt-identify.org]]), which also
   reverses =plans/public-api.org= § BOUNDARY — deliberately, argued in
   § BOUNDARY -- RESOLVED. Two behavior changes worth knowing before reading
   the R2 oracle numbers below. First, where several CRSes fit a WKT equally
   well it now reports *all* of them instead of taking the first in =NAMES=
   order, so the "327/431 resolved" figure below became 218 unique + 109
   ambiguous + 104 unidentified. Second, on 2026-08-19 the ellipsoid extractor
   learned two shapes it had been silently declining on — *spheres* (WKT writes
   inverse flattening =0=, PROJJSON a =radius=, so an Esri sphere could never
   match the registry's) and *non-metre axes* (wrapped with a
   =conversion_factor=) — which took that corpus to *321 unique + 110 ambiguous
   + 0 unidentified*, and the projected one from (1306, 890, 78) to
   (1383, 891, 0). Every one of the 2,705 real Esri rows now identifies. Found
   by =projjson-identify.org='s strip-id oracle; see its § RESULTS.

For current state rather than history, start at
[[file:project.org][project.org]] and [[file:plans/todo.org][plans/todo.org]].

** TL;DR
Geosetta carries a CRS through its IR opaquely and *labels but never reprojects*.
Milestones A/B/C of =geosetta/plans/crs.org= are *shipped* (CRS-loss warnings,
WKT-id lifting, and structural WKT→PROJJSON translation for WKT2 + "certain"
WKT1). The active decision is a *pivot*: instead of translating CRS strings, embed
PROJ's whole =proj.db= and resolve *(authority, code) → authoritative definition*.
That data carries third-party terms, so it lives in a *separate crate*
(=geoscribe=, this directory) behind a =crs-registry= Cargo feature; the
core =geosetta= crate stays pure-MIT and dependency-free. The plan is
=plans/crs-registry.org= (milestones R1–R5); the container format is =plans/registry-format.org=
(=GCR1=). *R1 is DONE, all four steps:* the generator + embedded blob (all
13 790 CRSes, =registry.bin.zst= = 637 KB); the reader (=src/crs/registry.rs=,
=OnceLock=-decoded, =def_projjson=/=def_wkt= via binary search); GeoParquet
=crs= emission routed through it for the trusted-id path
(=NamedCrs::registry_projjson=, tried before WKT translation); the
=--features crs-registry= rebuild hint on the GeoParquet id-reference warning
(=#[cfg(not(feature = "crs-registry"))]=); and the full identify oracle
(13 756/13 790 @ 100%, the remaining 34 an exhaustively-checked =projinfo=
limitation, not a registry defect — see KEY FINDINGS). Verified end-to-end
against a real GeoPackage (GDA2020/EPSG:7844): registry-resolved and
structurally-translated PROJJSON are byte-identical where both apply. Also done
since: =NamedCrs.code= is now =Option<String>= (was =Option<i64>=) across the
whole =geosetta= IR — a prerequisite for R2/R4 ever surfacing an IGNF/OGC/PROJ/
NKG alphanumeric code, see KEY FINDINGS. *R2 is now DONE — geographic
(2026-08-12) and projected (2026-08-12).* =registry::resolve_geographic_by_name=
/ =resolve_projected_by_name= look up an id-less WKT's outer name in =NAMES=
and validate it against its base ellipsoid (relative =1e-6=) before snapping —
never trusted outright. Geographic verified on the plan's own three worked
examples (all now resolve correctly, including the two the plan measured as
*wrong* under structural translation alone) and at scale: a 431-fixture bulk
oracle over every native ESRI geographic CRS in =proj.db= resolves *327/431
(76%), zero wrong*. Projected — originally scoped as the much heavier
"structural param-match" (method+parameter crosswalk, the plan's "recovery
3") — turned out not to need that at all: the *same* ellipsoid-only check
already suffices, proven by a 2 274-fixture bulk oracle (every native ESRI
projected CRS in =proj.db=) at *2185/2274 (96%) resolved@100%, zero wrong*
(11 hit an already-documented R1 =projinfo --identify= gap, not a defect).
See KEY FINDINGS and =plans/crs-registry.org='s R2 section for the full writeup,
including why axis order (what sank structural *translation* for projected
Esri) was never a risk for name *recovery*. *R3 is now DONE* (closed
2026-08-16, no code changes — see KEY FINDINGS): its "delete what the
registry makes redundant" framing would have regressed the *default*
(=crs-registry=-off) build if taken literally, since the crosswalk it wants
to trim is shared, unconditionally-compiled code, not feature-gated; closed
instead via option (a) — R1/R2's registry-first try-order already achieves
"structural path becomes validator/fallback" in behavior, so no crosswalk
deletion was made. *R4 is DONE* (implemented and
shipped 2026-08-12, in geosetta 0.21.0) — =geosetta/plans/shapefile.org= (full
Shapefile:
=.shp=/=.shx= geometry incl. ring-classification for Polygon/MultiPolygon,
=.dbf= attributes, =.prj= CRS), registered in =plans/README.org=. Read+write,
both directions, including GeoPackage↔Shapefile fan-out; =.prj= writing is the
first consumer of R1's =registry::def_wkt=. See § SHAPEFILE (R4) MILESTONE
DETAIL below. *R5 is DONE* (2026-08-12): WKT2:2019 added to the registry blob
(=GCR1= bumped =v1= → =v2=, =plans/registry-format.org= § V1→V2) and a new
=registry::def_wkt2=, closing the ~4% gap WKT1 can't express (datum
ensembles, dynamic CRSes, some compound) — proven, not assumed, by a new bulk
oracle: every one of the 13 790 entries now has WKT2, 13 735 self-identify at
100%, the other 55 an exhaustive documented =projinfo --identify= allowlist
(34 carried over from R1's own gaps turning out to be format-independent, 21
new WKT2-specific ones). Wired into GeoPackage's =.gpkg= writer as the
=definition_12_063= CRS-WKT extension column, verified end-to-end (writing
=EPSG:4979=, Geographic 3D, produces a real WKT2 string where WKT1 has none).
Found and fixed a real generator bug along the way: a few EPSG =AREA=
descriptions carry a literal embedded newline in the source data that broke
the line-based section parser under =--single-line=, silently truncating two
CRSes' WKT2 — see KEY FINDINGS.

** THE DECISION / PIVOT (why the registry)
Structural WKT→PROJJSON is only reliable when the input is *complete + carries an
authority id* (WKT2 always; GDAL WKT1 via the oracle-gated crosswalk). It *breaks*
on id-less inputs — the case that matters for the *Shapefile* spoke (now DONE,
see § SHAPEFILE (R4) MILESTONE DETAIL), whose =.prj= is *Esri-flavor WKT1* (no
id, no =AXIS=, non-standard datum names).
Verified: id-less Esri geographic mis-identifies (NAD83 → EPSG:9309, WGS84 → 70%);
projected Esri is axis-ambiguous and declines. Root cause is the *missing id*, not
parsing. The fix is *name → (authority, code) → authoritative definition*, all
derivable at build time from =proj.db=. See =plans/crs-registry.org= for the full
argument, sizes, and identity-recovery/validation design.

** KEY FINDINGS (so you don't relearn them the hard way)
- *The id does NOT override a wrong axis order.* Forcing easting/northing on a
  north/east CRS (EPSG:3034) identifies at 25–50 % *even with the correct id* —
  PROJ validates structure vs. the id. So projected CRSes need the *real* axis
  order; you can't shortcut it.
- *name→code resolves cleanly.* =proj.db='s =alias_name= (=source='ESRI'=) +
  each CRS table's =name= column map names→codes; a prototype resolved 7/7 of the
  hard Esri cases at 100 %.
- *Full universe = 13 790 CRSes* (all authorities: EPSG 7724, ESRI 2991, IAU_2015
  2201, IGNF 864, OGC 4, PROJ 4, NKG 2; all types). Embedded as compact
  PROJJSON+WKT1; *AS-BUILT with =zstd -19= = 637 KB* (28.7 MB raw) — well under the
  ~2.27 MB gzip estimate. *457* CRSes (3.3 %) have no faithful WKT1 (=has_wkt=0=;
  PROJJSON only → WKT2 deferred to R5).
- *Codes are STRINGS, not integers.* =IGNF= (864), =OGC=, =PROJ=, =NKG= use
  alphanumeric codes (=OGC:CRS84=, =IGNF:AMANU49G=, max 26 chars). The skeleton's
  =NAMES: …i64= was a latent bug — now =(&str name, &str auth, &str code)=; the
  =GCR1= key is =(auth_id, code_bytes)=. *Don't reintroduce an integer code type.*
- *Generator gotcha (fixed): =projinfo= prints per-format sections; a format it
  can't emit (WKT1 for Geographic-3D etc.) leaves an *empty stdout section* and puts
  the reason on *stderr*.* A naive "next non-empty line" parser spills into the next
  section (once stored =PROJJSON:= as the WKT value). =parse_sections= must not cross
  header boundaries — this is why the first run wrongly reported =no WKT1: 0=.
- *zstd compatibility is confirmed.* geosetta's from-scratch =compress/zstd.rs=
  decodes the =zstd -19= blob exactly, including a 28.7 MB multi-block frame with
  cross-block back-references. Compress with the =zstd= CLI at =-19=, *no* =--long=,
  *no* dictionary (the decoder handles a single plain frame only).
- *Generator gotcha #2 (found + fixed by the full oracle run): the plural
  =\"usages\"= array survived stripping as empty objects.* =STRIP_KEYS= removed
  =scope=/=area=/=bbox= recursively but not the *container* key =usages= (used
  when a CRS has multiple scope/area pairs), so =strip_usage= emptied each
  element to =\{\}= and left =\"usages\":[\{\},\{\}]= — structurally invalid
  PROJJSON that =projinfo= rejects outright ("missing children in usages
  child"). Fixed by adding =usages= to =STRIP_KEYS= (it's whole-key strippable,
  same as the singular fields); blob regenerated. *This only showed up once the
  reader existed and the full 13 790-entry oracle actually ran* — the earlier
  single-lookup smoke test (=EPSG:3857=) couldn't have caught it. *Lesson: don't
  trust a generator's "DONE" status until its own oracle has run end-to-end
  against the real reader, not a throwaway prototype.*
- *=projinfo --identify= cannot reach literal 100% over the whole universe, and
  that's not a bug.* After the =usages= fix, the full-registry oracle is
  13 756/13 790 (99.75%) @ 100%; the other 34 are a proven =projinfo= limitation
  (verified by feeding =projinfo=' own unstripped, authoritative export back into
  =--identify= and getting the identical result): (1) *all 15* EPSG
  =EngineeringCRS= entries — =--identify= returns zero matches for the whole
  type, categorically; (2) 19 ESRI UTM-zone/Alaska-system codes that are exact
  numeric duplicates of an EPSG CRS — =--identify= reports the EPSG twin at
  70–90% instead of the ESRI code at 100%. Encoded as an exhaustive
  =KNOWN_IDENTIFY_GAPS= allowlist in =registry.rs='s oracle test (asserts no
  *unexpected* failure and no *stale* exception — not a blanket tolerance). User
  decision (2026-08-12): allowlist over a bare threshold, so any *new* gap still
  fails loud.
- *Esri structural translation was TRIED AND REVERTED — do not re-attempt it.*
  Adding Esri to the crosswalk yielded *0* safely-verifiable oracle fixtures under
  strict-fallback (Esri omits =AXIS=, so nearly every real Esri CRS is
  axis-ambiguous; Web Mercator's aux-sphere param has no EPSG equivalent). The
  registry (name→code) is the right tool, not more structural parsing.
- *=en_default_safe= must be population-based.* It gates whether a no-=AXIS= WKT1
  may default to E/N; computing it from the sampled =cap= (not the full EPSG
  population) mislabels undersampled non-EN methods. Already fixed in the
  generator; keep it population-based.
- *=NamedCrs.code: Option<i64>= was a real gap, now fixed to =Option<String>=.*
  Found while scoping R2: the IR couldn't represent IGNF/OGC/PROJ/NKG's
  alphanumeric codes at all (=parse::<i64>()= calls silently dropped them, e.g.
  =OGC:CRS84= embedded in a WKT id never got lifted). Fixed crate-wide
  (=crs.rs=, both GeoPackage/FlatGeobuf readers+writers, GeoParquet's
  =parse_crs=/=crs_projjson=, =convert.rs= tests). Two formats are *irreducibly*
  numeric on disk regardless of the IR — GeoPackage's =srs_id=/
  =organization_coordsys_id= are SQLite =INTEGER= columns (plus a raw i32 in
  every geometry's GPB header) and FlatGeobuf's =Crs.code= is =int32= in its
  FlatBuffers schema — so a non-numeric code now falls back gracefully (a
  synthetic srs_id for GeoPackage, dropped-but-org/wkt-preserved for
  FlatGeobuf) instead of failing to compile the type. GeoParquet's PROJJSON

  evidence (each name is unique to one =(authority, code)= in =proj.db=); the
  ellipsoid check exists to catch a same-spelled name landing on the wrong
  *datum*, not to disambiguate *projection method* — so skipping the method
  check doesn't introduce ambiguity the way it would have for structural
  *translation* (which has to emit a specific method, not just accept-or-
  decline a candidate). Axis order — the actual root cause that sank
  projected *structural translation* (Esri omits =AXIS=, so translation had
  to guess it) — was never at risk here either: name recovery only reads the
  source WKT to *identify* which candidate to snap to; the emitted definition
  is the registry's own authoritative one, correct axis by construction. The
  11 "wrong-looking" results that did surface were re-checked and are exactly
  R1's already-documented =KNOWN_IDENTIFY_GAPS= (Complex-UTM zones snapping to
  their live EPSG twin over a deprecated ESRI code) — a =projinfo --identify=
  limitation, not a resolver defect; the oracle now filters these the same
  way R1's full-registry oracle does. *Lesson: an earlier "this will need a
  crosswalk" prediction is worth re-testing empirically once real fixtures
  exist, not treated as settled — the risk that killed structural
  translation (method/parameter spelling gaps) didn't actually apply to
  validation once measured.*
- *PROJJSON's ellipsoid flattening comes in two spellings — handle both.*
  Most ellipsoids carry =inverse_flattening= directly (matches WKT1
  =SPHEROID='s convention), but some (e.g. Clarke 1866 / NAD27) carry
  =semi_minor_axis= instead. Convert via =inverse_flattening = a / (a - b)=;
  verified exactly against Esri's own NAD27 export (=294.978698213898=
  computed from =a=6378206.4, b=6356583.8= matches to all given digits).
  Also: WGS 84-style ensembles put =\"ellipsoid\"= once at the
  =datum_ensemble= level (not per-member) — check =datum= first, fall back to
  =datum_ensemble=, same shape either way.

  =GEOGCS[\"GCS_WGS_1984\", ...]= spelling round-trips exactly because
  =gen_crs_registry.py='s =read_names()= already pulls =alias_name= rows
  =WHERE source='ESRI'= — the exact string a real Esri =.prj= would carry is
  already an index entry. No fuzzy matching, no crosswalk table needed for
  this half of R2.

  bulk oracle (every native ESRI geographic CRS in =proj.db=, real id-less
  =WKT1_ESRI= exports — =tools/gen_esri_geographic_fixtures.py= in this repo)
  resolves 327/431 (76%) with *zero* wrong snaps; declines cluster around
  auxiliary-sphere CRSes (a genuinely different ellipsoid — correctly
  declining) and IAU_2015 planetary bodies (moons — not yet root-caused, low
  priority since declining is already the safe outcome). Confirms the
  strict-fallback discipline holds under real breadth, not just the three
  cases the plan happened to measure by hand.
- *R3's "delete what the registry makes redundant" framing was a trap for the
  default build — closed instead via option (a), not implemented literally
  (user decision, 2026-08-16).* =geosetta/src/crs.rs= only feature-gates the
  registry module itself (=#[cfg(feature = "crs-registry")] mod registry;=);
  =wkt_projjson.rs=/=wkt1_tables.rs= (the structural crosswalk) are compiled
  *unconditionally*, shared by both builds. The default (=crs-registry=-off)
  build has *no* fallback if crosswalk coverage is deleted — it's the default
  build's *only* resolution mechanism, not a redundant validator, for anyone
  without the feature on. Any literal deletion of crosswalk entries "because
  the registry covers that code" would silently regress default-build
  correctness with nothing to replace it, directly breaking the
  degraded-mode contract's own promise. Two honest versions of R3 were
  weighed: (a) don't delete anything — R1/R2's priority ordering (registry
  tried first) already achieves "structural path becomes validator/fallback"
  in *behavior*, so R3 is largely already done; or (b) feature-gate the
  crosswalk itself so each build gets its own coverage — materially bigger
  (two maintained crosswalk surfaces) and doesn't even shrink the default
  build, only the feature build's compiled size. *Chosen: (a), closed, no
  code changes.*
- *=--single-line= is not a hard guarantee — a handful of EPSG =AREA=
  descriptions carry a literal embedded newline byte in the source data
  itself, found by R5's WKT2 bulk oracle (2026-08-12).* Two EPSG codes
  (=32075=/=32665=, sharing the "Gulf of Mexico ... Amery Terrace" area) had
  their WKT2 silently truncated mid-string by =gen_crs_registry.py='s
  line-based =parse_sections=, which took only the *first* non-empty line per
  section — the embedded newline split one logical section across two
  physical lines with *no* blank-line separator (a real separator between
  *different* sections always has one), so the second physical line was
  dropped rather than appended. Root-caused by directly reproducing one
  failing =projinfo= call and diffing line counts, not by guessing. Fixed by
  rewriting =parse_sections= to *accumulate* lines until the next real header
  (a blank line only closes a section once content has started) — this is
  the second time a generator "DONE" status turned out to be wrong only once
  the full bulk oracle actually ran (see the =usages= bug, R1), not a
  smaller smoke test. *Lesson, restated because it needed restating:* run the
  real oracle before trusting a generator, every time a generator changes,
  not just once.
- *A code can self-identify via PROJJSON but not via WKT2 — these are
  disjoint =projinfo --identify= gap sets, not the same gap in two dialects
  (found by R5's oracle, 2026-08-12).* 21 ESRI codes (20 deprecated
  geographic CRSes with a live successor, plus =ESRI:102113='s aux-sphere Web
  Mercator ambiguity — the same *kind* of ambiguity as R1's ESRI-UTM-
  duplicate gaps, just against WKT2) resolve at 100% via their PROJJSON but
  only 25–70% via their own WKT2 — verified individually (e.g.
  =ESRI:104009=) by feeding each serialization back into =--identify=
  separately. Conversely, R1's original 34 =KNOWN_IDENTIFY_GAPS= (mostly
  EngineeringCRS + exact-EPSG-duplicate ESRI codes) turned out to be
  *format-independent* — they fail under WKT2 too, not a PROJJSON quirk as
  the R1 writeup's phrasing might suggest in isolation. Net: two allowlists
  (=KNOWN_IDENTIFY_GAPS=, =KNOWN_WKT2_IDENTIFY_GAPS= in =registry.rs=), the
  WKT2 oracle checks membership in *either*, and *don't assume a gap found
  under one serialization automatically explains a gap under another* — each
  needs its own oracle run to confirm, which is exactly why R5 built one
  instead of reusing R1's verbatim.

** MAINTAINABILITY — detecting upstream drift (partially implemented; discussed 2026-08-12)
=proj.db= isn't static — EPSG/ESRI/IGNF/PROJ release periodically, adding
CRSes, editing definitions, deprecating codes. Two different concerns, both
currently underserved:

*** What already exists (correctness, once you've decided to regenerate)
- =DATASET_VERSIONS= (blob + =generated.rs= mirror) stamps EPSG/PROJ/ESRI/
  IGNF/NKG version numbers straight from =proj.db='s own =metadata= table,
  plus a generation date. Rerunning the generator against a newer =proj.db=
  and diffing this tells you immediately whether the *source* moved, and to
  what version.
- =CRS_COUNT= is checked against the blob header on every =cargo test= (fast,
  not =#[ignore]='d) — free drift detection on total entry count, no manual
  step needed.
- The bulk oracles (§ HOW TO VERIFY above) are the actual correctness gate:
  rerun after any regeneration and they fail loud if anything stops
  self-identifying.
- =KNOWN_IDENTIFY_GAPS=/=KNOWN_WKT2_IDENTIFY_GAPS= are *exhaustive*, not
  tolerant — a new gap fails the oracle, and a *stale* (now-fixed) one also
  fails ("on the list but now passes — remove it"). This is already the right
  shape for catching drift precisely, not just tolerating a bulk pass rate.

*** The actual gap: nothing says *what* changed between two runs
None of the above tells you *which* CRSes were added, which definitions were
edited, or whether a name→code mapping shifted — only that the count changed
or the oracle now fails somewhere.

** DEGRADED-MODE CONTRACT (feature off vs on)
Conversion never fails either way; only CRS-resolution fidelity changes.
- *Without =crs-registry=* (pure-MIT): handle *WKT2 + certain WKT1* (the
  oracle-gated crosswalk) structurally, as today. "Bad" WKT1 (id-less Esri,
  ambiguous, no-AXIS non-EN) and bare codes → *id-reference + warning*; the warning
  gains a hint to rebuild with =--features crs-registry= (scoped to the GeoParquet
  warning in =Crs::downgrade_warning=).
- *With =crs-registry=*: registry → structural → warn; the hard cases resolve and
  the hint stops firing. Structural becomes validator + custom-CRS fallback.

** SHAPEFILE (R4) MILESTONE DETAIL (done; implemented and shipped 2026-08-12, geosetta 0.21.0)
Full read+write =plans/shapefile.org= spoke, both directions (see
§ WHAT WAS COMMITTED vs UNCOMMITTED AT HANDOFF TIME for the file list).
- *Geometry* (=src/shapefile/geometry.rs=): mixed-endian =.shp=/=.shx= codec —
  BE file/record headers, LE shape-record content, exactly as the ESRI spec
  requires (no blanket endianness). Point/MultiPoint/LineString/
  MultiLineString are a direct structural copy; Polygon/MultiPolygon needed
  real geometry code — shoelace-formula signed area classifies each ring
  (negative = clockwise = shell, positive = counter-clockwise = hole), and
  rings are grouped into polygons by *appearance order* (a shell followed
  immediately by its holes), not full point-in-polygon containment, per the
  plan's own cost/benefit call — no fixture found yet that needs the fallback.
  The writer *normalizes* winding on emit (shell forced CW, holes forced CCW)
  regardless of input winding, so a round-tripped polygon can come back with
  reversed-but-geometrically-identical ring vertex order — expected, not a
  bug (unit tests use pre-wound fixtures to get bit-exact round trips).
  Z/M/MultiPatch shape types are out of scope, matching the existing 2D-only
  stance for GeoParquet/FlatGeobuf. A =.shp= can only declare *one* shape
  family (Point xor MultiPoint xor PolyLine xor Polygon); writing a
  =FeatureCollection= that mixes families, or contains a
  =GeometryCollection= (Shapefile has no equivalent shape type at all),
  errors rather than guessing — strict fallback, same rule as CRS.
- *Attributes* (=src/shapefile/dbf.rs=): dBase III/IV codec. Field width is
  data-driven (sized to the longest observed value per column, like
  GeoParquet's schema inference), not fixed — Int64 capped at 20 bytes (full
  =i64= range), Double at a fixed 6 decimals, String capped at DBF's 255-byte
  limit with *silent truncation at a UTF-8 char boundary* (the plan's open
  question on truncation policy — resolved this way since no other format in
  the crate has a per-field width cap to set a stricter precedent). Encoding:
  =.cpg= UTF-8 is honored exactly; anything else (or its absence, on a UTF-8
  decode failure) falls back to a from-scratch Latin-1 decode (byte value =
  Unicode code point) — not a real Windows-1252 table, a documented gap per
  the plan's own open question, kept to stay dependency-free. Memo (=M=)
  fields decode as =Null= (out of scope, needs a companion =.dbt=). Deleted
  records (=.dbf='s 1-byte flag) are dropped in lockstep with their
  same-position =.shp= record — =.shp= has no deletion flag of its own, so
  =.dbf= and =.shp= must be skipped together by row index, not independently.
- *CRS* (=.prj=): needed *zero new CRS code*, exactly as the plan predicted —
  reading is a direct call to =Crs::from_authority_code(None, None, Some(wkt),
  None)=, so R2's id-less-Esri-geographic name recovery activates automatically
  the moment =.prj= bytes reach it. Writing prefers the source's own verbatim
  WKT, else — with =crs-registry= on — =NamedCrs::registry_wkt= (=def_wkt='s
  first consumer); a =Crs::Wgs84= source writes a hardcoded canonical
  Esri-flavor WGS 84 WKT1 string (the exact id-less text real Esri =.prj=
  files carry — no registry needed for the common case). *Gotcha found via
  manual CLI testing, not a bug*: writing =Crs::Wgs84= to =.prj= and reading it
  back does *not* recover =Crs::Wgs84= without =crs-registry= on — the written
  text has no =AUTHORITY= node (matching real Esri files), so
  =from_authority_code='s WKT-id-lift finds nothing and it comes back as an
  id-less =Crs::Named=. A subsequent GeoJSON conversion of that round-tripped
  value then warns ("source CRS is the source CRS" — =NamedCrs::label='s
  existing fallback text for an all-=None= CRS, pre-existing/tested elsewhere,
  just newly reachable via a real code path). This is the *intended* degraded-
  mode behavior per the DEGRADED-MODE CONTRACT, not something to fix in the
  Shapefile spoke — real GDAL/PROJ resolve this by name-matching the same way
  R2 does, and even *with* =crs-registry= on, this specific GeoJSON warning
  still fires, because =downgrade_warning='s =GeoJson= arm warns for any
  non-collapsed =Crs::Named= unconditionally (registry recovery only feeds
  per-target *expressibility* checks like =registry_projjson=/=registry_wkt=,
  never the stored =Crs= variant's identity/collapse) — confirmed intentional
  by checking =wgs84_never_warns='s existing test coverage, not a regression.
- *Multi-file I/O* (=src/main.rs=): =read_input=/=write_collection= are the new
  shared choke points — every call site that used to do
  =std::fs::read=+=convert::read_features= or =convert::write_features=+

  =Format::Shapefile= (locate/write siblings by swapping =.shp='s extension,

  to one =layer.shp= sibling set per layer with no GeoPackage-side code

** CONVENTIONS / CONSTRAINTS
- *Strict fallback:* never emit a wrong/guessed CRS — a wrong CRS is worse than an
  unresolved one. Every translation is gated to =projinfo --identify= 100 %.
- *Dependency-free by default:* the core =geosetta= crate must not gain runtime
  deps; the registry is opt-in and its codec is Geosetta's own from-scratch zstd.
- *Never reproject* — Geosetta labels/translates identity only.
- *Commits:* the user commits deliberately (don't commit unbidden). *Do NOT add a
  =Co-Authored-By= trailer* to commit messages in this project (explicit user
  preference).
- Plans are org-mode; match the house style.
